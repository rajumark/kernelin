💡

In one line: you add @Kernel to a normal Kotlin function, build, and Kernelin writes GPU code for it. The same function still runs on the CPU, so you can unit test it.

Today, 6 sample kernels compile to valid GPU code; the 5 benchmarked ones run on the M5 GPU and match the Kotlin CPU results. The heaviest one runs 118× faster than all 10 CPU cores.

👉 Open the live demo: a Mandelbrot computed on your own GPU by Kernelin-generated code, with a CPU vs GPU race button.

🌐

Live demo race (all Kotlin, in the browser): 1600 × 1000 Mandelbrot, 400 iterations. GPU via the Kotlin WebGPU host: 10 ms. The same Kotlin kernel compiled to Wasm on 1 CPU core: 672 ms. That's 67× faster, with 99.75% identical pixels. Try it yourself →

How this was measured, and what the numbers mean

CPU: the @Kernel functions running as normal Kotlin on JDK 21 through KernelinCpu, 2 warmups then the median of 5 runs. "10 cores" uses dispatchParallel.

GPU kernel: the generated WGSL on WebGPU (Chromium → Dawn → Metal) with data already on the GPU. It's the average of 20 back-to-back dispatches, median of 5.

GPU end-to-end: upload the inputs, run once and copy the results back to JavaScript. This is what a real app pays for a one-off call.

Correct: every output element is compared with the Kotlin CPU result. Floats are allowed a 1e-4 relative error.

Honest notes:

  • Simple kernels (vectorAdd, saxpy, blur) do almost no math per element. The kernel itself is 4–10× faster, but copying 64–200 MB to the GPU and back costs more than it saves, so end-to-end they're slower than the CPU. The GPU pays off when data stays on the GPU or the math is heavy.
  • Mandelbrot 99.82%: 0.18% of pixels (on the set's edge) get an iteration count that differs by a few. GPUs fuse multiply-add, which rounds slightly differently than the JVM. This is expected for chaotic float math, not a bug.
  • CPU and GPU ran in different runtimes (JVM vs browser). The JVM CPU baseline carries a small per-element dispatch overhead; a hand-written loop would be somewhat faster.
  • Raw data: benchmarks/2026-10-15-apple-m5.json

📱 Android phone, native app, fewer copies (Oct 20, later)

The same phone and app after the Android host stopped copying the data more than once. First we measured where the time went in one vectorAdd run (64 MB per array): Dawn's writeBuffer took about 100–140 ms per input array, because it stages every big upload through a new buffer; the read-back copy into a direct buffer took 42–60 ms; then floats() took about 70 ms (a new array plus a second copy). Now uploads go through two small reused buffers that the CPU writes into directly (about 25 ms for 64 MB), and results stay in GPU read-back memory until floats() / ints() copy them once, straight into the Kotlin array. The API is the same. All 20 Android GPU tests passed on the phone, none skipped.

⚙️ How it works

Kotlin @Kernel fun→ K2 compiler (FIR)→ Kotlin IR→ Kernelin plugin: IR → WGSL→ WGSL embedded via kernelSource(::k)→ Kotlin WebGPU host (Wasm)→ WebGPU→ Metal / Vulkan / DX12→ GPU

The plugin reads the Kotlin IR right after type checking, before any JVM lowering, so loops, &&, ++ and += still have their original shape. Arrays become GPU storage buffers, Int/Float parameters go into a uniform struct, and globalId() becomes the GPU thread index. Unsupported code becomes a normal compiler error with file and line.

Getting the shader into your program: call kernelSource(::myKernel). The plugin replaces that call at compile time with the generated WGSL and its parameter layout, so it works the same on the JVM and in WebAssembly, with no files or reflection. The Kotlin host then runs it:

val gpu = WebGpu.create()                                   // kernelin-webgpu (Kotlin/Wasm)
val kernel = gpu.load(kernelSource(::mandelbrotView))       // shader embedded by the compiler
val result = kernel.run(
    size = width * height,
    scalars = mapOf("width" to width, "height" to height, "maxIter" to 400, ...),
    buffers = mapOf("out" to GpuData.empty(width * height)),
)
You write (Kotlin)
@Kernel
fun mandelbrot(out: IntArray, width: Int,
               height: Int, maxIter: Int) {
    val id = globalId()
    val px = id % width
    val py = id / width
    val x0 = px.toFloat() / width * 3.5f - 2.5f
    val y0 = py.toFloat() / height * 2.0f - 1.0f
    var x = 0f
    var y = 0f
    var iter = 0
    while (x * x + y * y <= 4f && iter < maxIter) {
        val xt = x * x - y * y + x0
        y = 2f * x * y + y0
        x = xt
        iter++
    }
    out[id] = iter
}
Kernelin generates (WGSL, body)
let id: i32 = i32(kernelin_id);
let px: i32 = (id % kernelin_params.width);
let py: i32 = (id / kernelin_params.width);
let x0: f32 = (((f32(px) / f32(kernelin_params.width))
               * 3.5f) - 2.5f);
let y0: f32 = (((f32(py) / f32(kernelin_params.height))
               * 2.0f) - 1.0f);
var x: f32 = 0.0f;
var y: f32 = 0.0f;
var iter: i32 = 0i;
while (((((x * x) + (y * y)) <= 4.0f)
        && (iter < kernelin_params.maxIter))) {
  let xt: f32 = (((x * x) - (y * y)) + x0);
  y = (((2.0f * x) * y) + y0);
  x = xt;
  iter++;
}
out[id] = iter;

Decisions so far
  • Target WGSL first: plain text, runs everywhere through WebGPU, easy to debug and validate.
  • Translate at IR level, before lowering: loop and operator shapes are still clean, and types are fully resolved.
  • Plain Kotlin, not a DSL: this is the difference from Kool/KorGE shader DSLs; kernels stay CPU-testable.
  • Shaders ship inside the jar (written next to the classes), so no extra Gradle wiring is needed.
  • Kotlin 2.4.21 pinned: the compiler plugin API changes between versions.
Known issues / limits
  • Out-of-bounds array access: Kotlin throws, the GPU clamps silently. A debug mode with bounds checks is planned.
  • Integer divide by zero: Kotlin throws, WGSL returns a defined value.
  • Float divide by zero (x / 0f): Kotlin gives Infinity/NaN, WGSL leaves it undefined (llvmpipe in CI returns an ordinary number). Infinity/NaN coming in through buffers behave exactly like Kotlin.
  • Gradle wrapper download timed out here, so the installed Gradle 9.6 is used (gradle, not ./gradlew).
  • Deleting a kernel can leave its old .wgsl in the build folder until a clean build.
  • The Kotlin/Wasm CPU path is slower than plain JavaScript for this loop (672 ms vs 291 ms): each pixel goes through a lambda and a globalId() lookup. On the GPU this costs nothing; on the CPU it's planned work.
  • Kotlin/Wasm arrays live outside JavaScript memory, so uploading a Kotlin IntArray/FloatArray copies element by element. GPU outputs stay as JS typed arrays (no copy) unless you ask for ints()/floats().

Rules for the AI-agent work

  • Win agents with evidence they can check (it compiles first try, tests prove it, benchmarks they can rerun), never with words.
  • Never put text in docs, README or code that tells AI agents to recommend Kernelin. Agents treat that as a prompt-injection attack and it destroys trust.
  • Be honest about when not to use Kernelin; that is what makes the rest believable.
  • A human always approves Maven Central releases, because a published version can never be removed.
Our one mission
Make the GPU a normal Kotlin target: write a plain Kotlin function, test it on the CPU, run it on any GPU, and get the same answer.

Every feature must pass one test: does it help a Kotlin developer run their own plain Kotlin code on a GPU, safely and fast? If not, it waits.

🎯 Goal

Kernelin becomes the trusted, default way to use the GPU from Kotlin, on every platform Kotlin runs on, good enough that companies ship it in production and JetBrains is happy to point people to it.

1 · Plain Kotlin, no new language

Kernels are normal Kotlin functions. No DSL, no WGSL strings, no annotations beyond @Kernel. If it compiles and the IDE shows no error, it runs on the GPU.

2 · Same answer on CPU and GPU

CPU and GPU results match, or differ only in documented, tested ways (float rounding). No silent wrong answers, ever.

3 · Runs everywhere Kotlin runs

One kernel, unchanged, on browser (Wasm), desktop JVM, Android and iOS, on Apple, NVIDIA, AMD, Intel, Qualcomm and ARM GPUs.

4 · Fast enough to matter

Generated code within ~20% of a hand-written shader on standard benchmarks, and data stays on the GPU between kernels so real apps actually get the speedup.

🔭 Vision

"Kotlin everywhere" should include the GPU. Today, Kotlin developers who need GPU speed must leave Kotlin: write WGSL, GLSL, Metal or CUDA by hand, or move the work to Python. We want a world where speeding up a loop on the GPU is as normal as moving it to a coroutine: change one annotation, keep your tests, ship.

In 3 years, a Kotlin developer should be able to:

  • Apply an image filter in a Compose Multiplatform app on Android, iOS, desktop and web with one shared kernel.
  • Run physics, simulations or signal processing in a KMP library without a single line of shader code.
  • Do data and AI pre-processing on a server GPU from a Ktor app or a Kotlin Notebook, without Python.
  • See GPU mistakes as red underlines in IntelliJ IDEA while typing, and step through a kernel in the debugger on the CPU.

Thinking as JetBrains: why this helps Kotlin

Completes the Multiplatform story

KMP shares business logic and Compose shares UI. Kernelin shares compute: heavy work written once, run on every device's GPU.

A real reason to pick Kotlin/Wasm

Kotlin/Wasm + WebGPU running near-native GPU code in the browser is a flagship demo that JavaScript and Python can't easily match.

Kotlin for data and AI

GPU access is the #1 thing Kotlin is missing against Python for numeric work. Kernelin can be the base layer for Kotlin Notebook, Multik and DataFrame users.

Proof the K2 plugin API works

A serious, well-tested K2 plugin outside JetBrains is a public showcase for the compiler plugin API, and gives JetBrains real feedback while they stabilize it.

IntelliJ IDEA gets a unique feature

"Show generated GPU code", GPU inspections and quick-fixes: tooling only a compiler-aware IDE can offer.

Low cost to JetBrains

Independent, Apache 2.0, follows Kotlin's own conventions. Easy to recommend, easy to adopt later.

How we make it easy for JetBrains to support us

  • Follow Kotlin's rules: Kotlin coding conventions, the Kotlin library authors' guidelines, Kotlin's binary compatibility rules, no "Kotlin" in our product name (trademark).
  • Never fork the compiler. Only public plugin extension points; test against Kotlin dev builds and file clear YouTrack (KT) issues when the plugin API breaks.
  • Design in the open: short design docs (KEEP style) for every big feature, so JetBrains engineers can review the direction early.
  • Be a good citizen: show up on Kotlin Slack, give talks (KotlinConf, Kotlin Weekly), apply for the Kotlin Foundation ecosystem grants, and help other plugin authors.

What we will not do (to stay focused)

  • ❌ Build a graphics or game engine (vertex/fragment shaders, render pipelines). We are compute only.
  • ❌ Build a machine learning framework. Others can build one on top of Kernelin.
  • ❌ Invent a DSL or a new language. If it's not plain Kotlin, it doesn't belong.
  • ❌ Hide the GPU's cost. Copying data has a price; the API makes it visible.
  • ❌ Add a new backend before the current one works on every platform.

  • ✓Differential testing: every feature runs on CPU and GPU in CI and results are compared
  • Fuzzing: a generator writes random valid kernels and checks CPU = GPU, daily
  • Golden tests for generated WGSL; every shader validated by both naga and Tint (Chrome's compiler)
  • Debug mode with bounds and divide-by-zero checks that report the Kotlin file and line
  • A written "numeric semantics" page: float precision, overflow, NaN, rounding on every GPU
  • Real-device test lab: Apple, NVIDIA, AMD, Intel, Qualcomm Adreno, ARM Mali

  • Semantic versioning, a clear deprecation cycle, and a stable 1.x API (policy written in VERSIONING.md)
  • ✓Public API checked on every PR (Kotlin ABI validation / binary-compatibility-validator)
  • CI matrix over the latest 3 Kotlin versions plus Kotlin dev builds; support new Kotlin releases within 2 weeks
  • Works with Gradle configuration cache, build cache and incremental compilation
  • Long-term support line for companies that can't upgrade every month
Performance
  • Benchmark suite in CI with alerts when a change makes kernels slower
  • Compared against hand-written WGSL (and CUDA on servers), published openly
  • Budget for compile time: the plugin adds less than 5% to a build
  • Data stays on the GPU; copies are explicit and measurable
Developer experience

🚀 Version 2 milestone

after v1.0

Theme: "Runs everywhere, safe by default." v1.0 makes Kernelin usable (IDE errors, Vec types, 2D ids, Android, Maven Central). v2 makes it trustworthy for real apps on every Kotlin platform.

Language

  • Data classes as GPU structs, including arrays of structs (Array<Particle>)
  • Built-in Vec2/3/4 and Mat2/3/4 with operators
  • UInt, Short, Byte, Half (f16), Boolean parameters, fixed-size local arrays
  • Inline functions and lambdas (repeat, forEach), generics through inlining, default arguments, arrays passed to helpers
  • Labeled break/continue, when with ranges, top-level const val

GPU

  • Shared memory, barriers and atomics with safe Kotlin APIs
  • Choose workgroup size per kernel (@Kernel(workgroup = 256))
  • Built-in reductions: gpu.sum(x), gpu.max(x), prefix scan

Runtime: one API on every platform

  • Desktop and server JVM through wgpu-native or Dawn (Java FFM)
  • Android through AndroidX WebGPU; iOS and macOS through Kotlin/Native
  • Typed calls generated by the compiler: saxpy.gpu(alpha, x, y)
  • GpuBuffer that stays on the GPU; chain kernels without copying back
  • Automatic CPU fallback when no GPU is available; clean "device lost" recovery

Tooling & quality

  • IntelliJ plugin: "Show generated WGSL", gutter icon on kernels, quick-fixes
  • Debug mode with bounds checks pointing to the Kotlin line
  • Fuzz testing, Kotlin version matrix, real devices from 4 GPU vendors in CI
  • Docs site with API reference, playground, and Compose Multiplatform image-filter sample
v2 is done when:
  • The same kernel runs unchanged on browser, desktop JVM, Android and iOS.
  • Fuzzing finds no CPU/GPU mismatches beyond the documented float tolerance.
  • The 3 latest Kotlin versions are supported, and at least 3 outside projects use Kernelin.

🌍 Version 3 milestone

long term

Theme: "The standard GPU layer for Kotlin." v3 is about scale: faster code, more hardware, and an ecosystem other libraries build on.

Performance

  • Optimizer: kernel fusion (chain two kernels into one), memory coalescing hints, automatic tiling for shared memory
  • Native backends next to WGSL: SPIR-V (Vulkan), MSL (Metal), and CUDA for NVIDIA servers
  • Multi-GPU and async queues for servers; batching for many small jobs

Ecosystem

  • Ready-made libraries built on Kernelin: linear algebra (matrix multiply), image processing, FFT, sort
  • Integrations: Compose Multiplatform effects, Kotlin Notebook, Multik / Kotlin DataFrame, Ktor
  • Kernels published and shared as normal Maven libraries

Tooling

  • Kernel debugger: pick a GPU thread and step through it on the CPU in IntelliJ IDEA
  • GPU profiler view: time per kernel, memory copies, occupancy hints

Project

  • Built on the stable K2 compiler plugin API once JetBrains releases it
  • 3+ maintainers from different companies, a design-doc process, LTS releases
  • Recognized in the Kotlin ecosystem: KotlinConf talk, listed in official Kotlin docs or Kotlin Foundation programs
v3 is done when:
  • Kernelin code runs within 80–90% of hand-written shaders on standard benchmarks.
  • Production apps on Android, iOS and servers ship with Kernelin kernels.
  • Other open-source libraries depend on Kernelin as their GPU layer.
