💡

In one line: you add @Kernel to a normal Kotlin function, build, and Kernelin writes GPU code for it. The same function still runs on the CPU, so you can unit test it.

Today, 6 sample kernels compile to valid GPU code; the 5 benchmarked ones run on the M5 GPU and match the Kotlin CPU results. The heaviest one runs 118× faster than all 10 CPU cores.

👉 Open the live demo: a Mandelbrot computed on your own GPU by Kernelin-generated code, with a CPU vs GPU race button.

Live demo race (all Kotlin, in the browser): 1600 × 1000 Mandelbrot, 400 iterations. GPU via the Kotlin WebGPU host: 10 ms. The same Kotlin kernel compiled to Wasm on 1 CPU core: 672 ms. That's 67× faster, with 99.75% identical pixels. Try it yourself →

How this was measured, and what the numbers mean

CPU: the @Kernel functions running as normal Kotlin on JDK 21 through KernelinCpu, 2 warmups then the median of 5 runs. "10 cores" uses dispatchParallel.

GPU kernel: the generated WGSL on WebGPU (Chromium → Dawn → Metal) with data already on the GPU. It's the average of 20 back-to-back dispatches, median of 5.

GPU end-to-end: upload the inputs, run once and copy the results back to JavaScript. This is what a real app pays for a one-off call.

Correct: every output element is compared with the Kotlin CPU result. Floats are allowed a 1e-4 relative error.

Honest notes:

  • Simple kernels (vectorAdd, saxpy, blur) do almost no math per element. The kernel itself is 4–10× faster, but copying 64–200 MB to the GPU and back costs more than it saves, so end-to-end they're slower than the CPU. The GPU pays off when data stays on the GPU or the math is heavy.
  • Mandelbrot 99.82%: 0.18% of pixels (on the set's edge) get an iteration count that differs by a few. GPUs fuse multiply-add, which rounds slightly differently than the JVM. This is expected for chaotic float math, not a bug.
  • CPU and GPU ran in different runtimes (JVM vs browser). The JVM CPU baseline carries a small per-element dispatch overhead; a hand-written loop would be somewhat faster.
  • Raw data: benchmarks/2026-10-15-apple-m5.json

⚙️ How it works

Kotlin @Kernel fun→ K2 compiler (FIR)→ Kotlin IR→ Kernelin plugin: IR → WGSL→ WGSL embedded via kernelSource(::k)→ Kotlin WebGPU host (Wasm)→ WebGPU→ Metal / Vulkan / DX12→ GPU

The plugin reads the Kotlin IR right after type checking, before any JVM lowering, so loops, &&, ++ and += still have their original shape. Arrays become GPU storage buffers, Int/Float parameters go into a uniform struct, and globalId() becomes the GPU thread index. Unsupported code becomes a normal compiler error with file and line.

Getting the shader into your program: call kernelSource(::myKernel). The plugin replaces that call at compile time with the generated WGSL and its parameter layout, so it works the same on the JVM and in WebAssembly, with no files or reflection. The Kotlin host then runs it:

val gpu = WebGpu.create()                                   // kernelin-webgpu (Kotlin/Wasm)
val kernel = gpu.load(kernelSource(::mandelbrotView))       // shader embedded by the compiler
val result = kernel.run(
    size = width * height,
    scalars = mapOf("width" to width, "height" to height, "maxIter" to 400, ...),
    buffers = mapOf("out" to GpuData.empty(width * height)),
)
You write (Kotlin)
@Kernel
fun mandelbrot(out: IntArray, width: Int,
               height: Int, maxIter: Int) {
    val id = globalId()
    val px = id % width
    val py = id / width
    val x0 = px.toFloat() / width * 3.5f - 2.5f
    val y0 = py.toFloat() / height * 2.0f - 1.0f
    var x = 0f
    var y = 0f
    var iter = 0
    while (x * x + y * y <= 4f && iter < maxIter) {
        val xt = x * x - y * y + x0
        y = 2f * x * y + y0
        x = xt
        iter++
    }
    out[id] = iter
}
Kernelin generates (WGSL, body)
let id: i32 = i32(kernelin_id);
let px: i32 = (id % kernelin_params.width);
let py: i32 = (id / kernelin_params.width);
let x0: f32 = (((f32(px) / f32(kernelin_params.width))
               * 3.5f) - 2.5f);
let y0: f32 = (((f32(py) / f32(kernelin_params.height))
               * 2.0f) - 1.0f);
var x: f32 = 0.0f;
var y: f32 = 0.0f;
var iter: i32 = 0i;
while (((((x * x) + (y * y)) <= 4.0f)
        && (iter < kernelin_params.maxIter))) {
  let xt: f32 = (((x * x) - (y * y)) + x0);
  y = (((2.0f * x) * y) + y0);
  x = xt;
  iter++;
}
out[id] = iter;

Decisions so far
  • Target WGSL first: plain text, runs everywhere through WebGPU, easy to debug and validate.
  • Translate at IR level, before lowering: loop and operator shapes are still clean, and types are fully resolved.
  • Plain Kotlin, not a DSL: this is the difference from Kool/KorGE shader DSLs; kernels stay CPU-testable.
  • Shaders ship inside the jar (written next to the classes), so no extra Gradle wiring is needed.
  • Kotlin 2.4.21 pinned: the compiler plugin API changes between versions.
Known issues / limits
  • Out-of-bounds array access: Kotlin throws, the GPU clamps silently. A debug mode with bounds checks is planned.
  • Integer divide by zero: Kotlin throws, WGSL returns a defined value.
  • Gradle wrapper download timed out here, so the installed Gradle 9.6 is used (gradle, not ./gradlew).
  • Deleting a kernel can leave its old .wgsl in the build folder until a clean build.
  • The Kotlin/Wasm CPU path is slower than plain JavaScript for this loop (672 ms vs 291 ms): each pixel goes through a lambda and a globalId() lookup. On the GPU this costs nothing; on the CPU it's planned work.
  • Kotlin/Wasm arrays live outside JavaScript memory, so uploading a Kotlin IntArray/FloatArray copies element by element. GPU outputs stay as JS typed arrays (no copy) unless you ask for ints()/floats().
